# Smart targeting capacity flow

`business_flow/smart_targeting_capacity_flow.go` coordinates durable, asynchronous exact-capacity calculations. A capacity generation describes an eligibility snapshot; it does not itself reserve concrete recipients. The [audience repository](smart-targeting-audience-repository.md) describes the actual population queries, and the [capacity repository](campaign-targeting-capacity-repository.md) describes durable leasing.

## Types and inputs

`SmartTargetingCapacityFlow` exposes start, polling and worker execution. `SmartTargetingCapacityFlowImpl` holds repositories and the database. `SmartTargetingCapacityConflictError` carries an existing calculation response; `SmartTargetingCapacityPendingError` unwraps to `ErrSmartTargetingCapacityPending`. `NewSmartTargetingCapacityFlow` constructs the flow; `smartTargetingDB` obtains a transaction from context if present.

`ownedSmartCampaign` validates ownership, bundle and smart-targeting context. `canCalculateSmartTargetingCapacity` governs allowed lifecycle states. `normalizeSmartTargetingScoreClasses` validates and canonicalizes grades; `sameSmartTargetingScoreClasses` compares them. `selectedSmartTagIDs` requires the selected tags, while `tagIDsToInt64` and `canonicalSmartTargetingCapacityTagIDs` convert them for PostgreSQL arrays. `smartTargetingCapacityPhase` determines the explicit test or execution phase. `smartTargetingTagHash`, `smartTargetingInputHash` and `hashSmartTargetingCapacityString` provide stable input identity; `calculationExpiry` determines the result's lifetime. `smartTargetingScoreClass` maps a score and percentile bounds to a class.

## Start and polling

`Start` validates the request, ownership, classes and campaign state. It then locks the campaign in a transaction and repeats state checks so a concurrent selection edit cannot produce a mixed snapshot. It derives platform and allowed colors, reads and validates the selected tags and, when explicitly requested classes differ, updates the editable campaign and clears its test preview. The input hash includes effective tags, classes, platform, colors and phase.

An unexpired active calculation for the same input is returned as the existing work; a different active generation is superseded, with a reload if another actor wins that transition. A calculated row is reused only if its entire snapshot and allocation state are still current. Otherwise a new calculating row is inserted with version, expiration and bundle exclusions enabled. The request returns promptly; the expensive scan runs in the worker.

`GetCurrent` resolves the appropriate calculation for the owned campaign; `GetByID` retrieves a specific owned generation. `statusDTO` and `capacityDTO` map state and freshness to the response; `int64ToUint64Ptr` and `ptrTime` handle optional values. `CurrentSmartTargetingCapacity`, `EnsureCurrentSmartTargetingCapacity` and `isCurrentSmartTargetingCapacity` validate persisted results for other flows. A completed result can become stale when input, expiration, algorithm version or allocation fingerprint changes; it must not be treated as current just because its status is calculated.

## Allocation state and execution

`smartTargetingBundleAllocationState` loads other bundle allocations and active reservations. `smartTargetingBundleAllocationStateFromRows` and `smartTargetingBundleAllocationStateFromRowsAndActiveTestReservations` build the deduction and fingerprint; `smartTargetingBundleAllocationFingerprint`, `approvedCampaignDeduction` and `emptySmartTargetingAllocationFingerprint` expose specific pieces. The fingerprint lets later consumers detect changed bundle usage without assuming a historical calculation is still valid.

`smartTargetingCapacityAudienceQuery` translates a calculation snapshot into the repository's explicit eligibility query. `ExecuteCampaignTargetingCapacityCalculation` performs the background scan and completes or fails the leased generation through the repository. The repository's `started_at` guard prevents a reclaimed worker from publishing. Capacity and available counts have different meanings: the raw tag union precedes bundle consumption and score filters, while eligible/usable values reflect the flow's constraints and deductions. Inspect the current snapshot and fingerprint when diagnosing a mismatch.

## Reading a capacity result

Consider two selected tags that each contain 100 profiles, with 40 in common. Adding their tag counts gives 200, but the raw unique union is 160. Bundle consumption, reservations, reachability, colors and selected score classes can reduce the eligible population further. The calculation records separate values precisely so a client does not confuse the sum of per-tag snapshots with usable unique capacity. The allocation fingerprint is an additional freshness check: even unchanged tags and scores do not make an old result current after relevant bundle allocations change.

When debugging a pending response, first check whether `Start` found the same active generation. For a stale or rejected result, compare phase, platform, canonical tags, score classes, allowed colors, version, expiration and allocation fingerprint; then inspect the worker lease and repository state. The flow's currentness checks are more stringent than simply finding a row with a matching hash.
