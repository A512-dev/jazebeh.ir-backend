# Bundle tag evaluation flow

`business_flow/bundle_tag_evaluation_flow.go` turns a bundle persona and the active tag catalog into an asynchronous, durable set of AI-generated fit scores. The entry point queues work; a worker executes it. The [evaluation repository guide](bundle-tag-evaluation-repository.md) explains the persisted run, event, attempt, batch and score records.

## Structure and request contract

`BundleTagEvaluationFlow` exposes request, status, score-list and worker execution methods. `BundleTagEvaluationFlowImpl` holds bundle/customer/tag repositories, repositories for each run record, a database, configuration, client factory and shared request pacer. `NewBundleTagEvaluationFlow` wires them. `openAIClientFactory` permits client construction to be substituted. `BundleTagEvaluationConflictError` carries the already-active run response; `BundleTagEvaluationDailyLimitError` carries the limit, submitted count and UTC reset time.

`RequestBundleTagEvaluation` rejects nil requests and disabled evaluation or scheduler configuration, verifies customer and bundle ownership, and checks for an active run. It snapshots the persona, prompts, configuration and batch size into a new run. Inside a transaction it locks the customer request scope and bundle, repeats the active-run check, checks the customer's UTC-day quota and writes the run and created event. The first active check is only an optimization; the locked recheck prevents simultaneous submissions. The response represents queued work, not completed scores.

`GetBundleTagEvaluationStatus` repeats ownership checks and returns a synthesized not-evaluated status when no read model exists. `ListBundleTagScores` checks ownership, defaults page/limit to 1/20, caps limit at 100 and maps the current score read model, including snapshots and score explanations. Current-score reads are restricted to active tags by the repository.

## Worker execution and recovery

`ExecuteBundleTagEvaluationRun` loads the run and acquires a bundle-scoped execution lock. Already evaluated runs return successfully. It reconstructs execution settings from the persisted snapshot, records a started event when needed, constructs a paced client, obtains persona analysis, ensures tag batches, processes batches concurrently and verifies score counts before recording completion. The permitted missing total is configured missing tags per batch multiplied by batch count. Failure is recorded through `failRunUnlessCanceled`; cancellation is kept distinct from an ordinary terminal failure.

`ensurePersonaAnalysis` first tries to reuse the latest successful persisted response, extracting text from the raw response if necessary. It will not automatically retry a previously non-retryable attempt. Otherwise it writes a start event, calls the provider with the snapshotted persona and prompt, saves attempts including response and usage information, and writes response/completion events. Retryable failures wait before another attempt, bounded by configured retries; cancellation stops work.

`ensureBatches` returns existing batches on resume. Otherwise it pages through active tags by ID, verifies each has required name, display title, persona and audience count, snapshots those fields, partitions them by the run's stored batch size and transactionally inserts batches and creation events. The snapshot prevents a retry from silently using different input. `processBatchesConcurrently` and `runBundleTagEvaluationBatchesConcurrently` coordinate bounded parallel work and propagate batch errors. `processBatch` records attempts and events, checks active tags, invokes the model, validates its response and persists scores; completed work can be recovered from durable state. `ensureBatchTagsRemainActive` guards against catalog changes during execution. `waitBeforeBundleTagEvaluationOpenAIRetry` handles retry delays and cancellation.

## Data validation and helper families

`parseAndValidateBatchResponse` and `decodeBundleTagScoreItems` decode and validate provider output against the expected batch. `buildBundleTagScoreRows` associates validated scores with frozen tag snapshots, and `insertBatchScores` persists them. `bundleTagScoreResult` and `bundleTagScorePayload` describe parsed results and request data. `buildPersonaAnalysisPayload` and `buildTagScoringPayload` construct provider requests; `buildResponsesAPIMessage` and `buildReasoningPayload` supply common message fields. `extractOpenAIResponseText` and `cleanupJSONText` normalize provider responses before parsing; `normalizeOpenAIResult` fills consistent attempt metadata.

The configuration snapshot types preserve prompt, model, batching and validation settings for recovery. `configurationSnapshot` creates it; `executionConfiguration` reconstructs it for the run. `bundleTagEvaluationRequestPacer` serializes request timing and can pause; `bundleTagEvaluationPacedOpenAIClient` applies that policy to provider calls. `shouldRetryOpenAIError`, `isSuccessfulAttemptStatus`, `nonRetryableAttemptError`, `nonRetryableBatchAttemptError` and `nonRetryableHTTPStatusError` classify retry behavior. The lock helpers serialize request creation and execution at their respective scopes; `bundleTagEvaluationUTCDayBounds` defines quota boundaries. Remaining pointer, proxy-redaction and JSON helpers support safe representation of persisted metadata.

When debugging, start with the run status and events, then inspect persona and batch attempts and the score count. A created run is not evidence that the provider succeeded; an attempt response is not a completed batch until validation and persistence succeed.

## Batch response and restart details

`processBatch` checks the completion event first. If the score count already equals the batch tag count, it records completion from existing scores without making another provider call. Otherwise it can reuse a successful saved raw response by parsing it again and persisting its scores. Only after those recovery paths does it decide whether a new attempt is allowed. Before each new call it checks that the snapshotted tags remain active; it records the request, response, status, provider ID, model, usage, timing and any error as an attempt. A provider success with invalid JSON is still a failed validation attempt, not a valid score.

`decodeBundleTagScoreItems` accepts either an array or an object containing a `scores` array. `parseAndValidateBatchResponse` rejects negative missing-tag allowance, empty output, malformed JSON, missing or duplicate tag IDs, scores outside 0–100, and blank fit level, relation type or reason. Exact-ID and exact-count checks depend on the validation configuration, but the missing-tag allowance is checked against the expected snapshots. A legacy `campaign_fit_score` can supply the score; conflicting legacy and `bundle_fit_score` values fail. The raw per-item JSON is retained alongside parsed values. This matters when diagnosing a run: an HTTP 200 can still be retried because its content failed these checks.

For a worked trace, a bundle with 125 active tags and batch size 50 produces batches of 50, 50 and 25. Each batch is snapshotted once. If a worker crashes after the second batch's scores are stored but before its completion event, the next worker can record the event from existing scores. Completion of the run still checks the total against the allowed missing count across all three batches.
