# Campaign flow: customer lifecycle, pricing and reports

`business_flow/campaign_flow.go` is the main customer campaign orchestration file. It covers creation and edits, finalization and wallet reservation, cancellation, capacity and cost, display, reports and refund reconciliation. It works with several other files whose methods share `CampaignFlowImpl`: [test sampling](smart-targeting-sampling-flow.md) and [execution calculation](smart-targeting-execution-calculation-flow.md). Read [campaign lifecycle](campaign-lifecycle.md) for the cross-layer path.

## Architecture and state

`CampaignFlow` declares the customer-facing operations; `CampaignFlowImpl` contains the repositories, database, pricing/configuration, notifier and other dependencies wired by `NewCampaignFlow`. DTO validation is only one layer: the flow also checks ownership, persisted state, references and financial invariants. Repository locks and database transactions protect state that can change between requests. Business errors translate lower-level failures into stable operation-facing codes.

The major distinction is draft versus finalization. Draft edits configure the campaign; finalization validates the effective configuration, establishes targeting intent and reserves money. Approval and execution are separate admin and bot flows. A smart-targeted campaign additionally depends on current capacity and, depending on phase, a test sampling preview or a ready execution proposal.

## Creation, editing and finalization

`CreateCampaign` calls `validateCreateCampaignRequest`, validates customer and related references, creates the campaign transactionally and records audit information. `createCampaign` builds the model/spec and persists it. `ensureCampaignBundleAndPhase`, `ensureCreateCampaignRefs` and `ensureUpdateCampaignRefs` enforce bundle, phase and related-entity rules. `validateCampaignPhaseInput`, `campaignPhasePtr` and `campaignPhaseOrDefault` handle phase representation and defaults.

`UpdateCampaign` first validates the request and loads the owned, editable campaign. It computes the effective post-update configuration before checking references. The implementation deliberately has two phases:

1. A short transaction locks and persists the spec changes. A changed smart test configuration can invalidate an in-flight sampling generation. Inactive targeting-method data is generally retained for future edits, subject to the explicit Excel/smart-targeting rules in `applyCampaignSpecUpdate`.
2. For finalization, capacity and pricing inputs are prepared outside the long financial transaction. Execution candidate discovery is not performed in this HTTP request: a ready durable proposal must already exist. The final transaction locks and rechecks the campaign, bundle, targeting state and wallet, reserves the budget and commits the relevant reservation and state change together. Notifications follow commit.

This split means a failed finalization does not necessarily undo an earlier successfully saved draft edit. `validateUpdateCampaignRequest`, `validateUpdateCampaignBudget`, `validateCampaignFinalizationBudget` and `canFinalizeCampaign` check different stages of that process. `applyFinalizedCampaignCost` records authoritative cost; smart test budget is derived from the actual sampling intent rather than a user-supplied amount. `smartTargetingTestSamplingConfigurationChanged` compares effective values so an unchanged full-form submission does not invalidate useful preview work.

`smartTargetingExecutionReservationPlan`, `reserveSmartTargetingExecutionAudience`, `executionReservationBusinessError`, `uint64ToUintSlice` and `firstMatchingSmartTargetingTag` adapt a calculated proposal and translate reservation failures. A proposal can become stale while waiting for the bundle lock, so it must be checked again inside finalization.

`applyCampaignSpecUpdate` is important for clients: most fields are sparse patches, but ad link, schedule and short-link domain use replace semantics, so absent/null/empty can clear them. `prepareAudienceTargetingUpdate`, `sanitizeAudienceTargetingMethod`, `resolveAudienceTargetingMethod`, `resolveAudienceTargetingMethodWithSelectedTags` and `campaignAudienceTargetingMethod` decide the effective standard, Excel or smart targeting mode, including legacy clients that omit an explicit method.

## Clone, visibility and cancellation

`CloneCampaign` creates a fresh campaign from an owned source with reset identity and lifecycle state; the source campaign lock serializes it with concurrent changes. `CancelCampaign` takes different financial paths depending on persisted status and uses the original financial transactions and wallet state. `HideCampaigns` and `UnhideCampaigns` normalize and scope campaign IDs to the customer; they affect visibility, not execution. `normalizeCampaignIDs` removes unsuitable/repeated IDs before bulk operations. `expireCustomerCampaigns` handles the expiry path separately. Follow the exact state branch and original transaction when reviewing a money movement; do not infer a refund from the UI status alone.

## Capacity and price

`CalculateCampaignCapacity` handles the applicable audience source. Standard targeting uses the database-backed audience specification, filters the requested hierarchy/tags and combines capacities. `calculateAudienceSpecItemCapacity`, `audienceSpecItemGradeCapacity` and `addAudienceCapacity` implement item/grade arithmetic and overflow checks. Excel targeting counts the uploaded audience; smart targeting uses its separate exact-generation lifecycle rather than relying on a sum of overlapping tag populations.

`CalculateCampaignCost` derives an affordable audience from budget and available capacity. `CalculateCampaignCostV2` starts from a requested message count: it caps ordinary requests to available capacity, but rejects a smart execution request above exact usable capacity. Both require a current smart test preview for test campaigns and use its effective sample size. `checkedCampaignCost` prevents multiplication overflow. Configured admin mobile accounts can receive zero total cost.

`computeCostInputs` obtains price and capacity. For smart targeting it requires `EnsureCurrentSmartTargetingCapacity`; pending, expired or allocation-stale generations cannot be used for financial reservation. For standard/Excel it uses the established capacity path. `computePricePerMessage` validates platform and required inputs, loads current platform base and page prices, derives message parts, and applies line and segment factors. In the current code SMS price is `base * uint64(lineFactor * parts) + uint64(segmentFactor * pagePrice)`; other platforms use one base unit plus the segment/page component. The conversion placement matters for fractional factors. `fetchLineNumberPriceFactor`, `fetchSegmentPriceFactor` and `notifyMissingSegmentPriceFactor` support this calculation.

`calculateParts` and `countCharacters` implement message sizing and link substitution. Non-SMS uses one part; SMS uses 70 characters for one part and 66 per concatenated part. `sanitizeShortLinkDomain`, `sanitizeCampaignPlatform`, `sanitizeAudienceGrades`, `campaignAudienceGradesOrDefault`, `sanitizeCategoryAndJob` and `ensureCampaignSpecDefaults` normalize and validate inputs. Schedule validation uses `isScheduleWithinTehranWindow` and `getTehranLocation`.

## Customer reads and reports

`ListCampaigns` validates the customer, builds repository filters and ordering, fetches a page, enriches click counts and statistics and returns pagination. `GetLastInitiatedCampaign` finds the latest relevant draft. `campaignDisplayEnrichments`, `fetchCampaignDisplayEnrichments` and `buildCampaignResponse` construct display values. `resolvePlatformBasePrice`, `resolveSegmentPriceFactor` and `resolveLinePriceFactor` prefer captured finalization metadata when available, falling back to current repositories; their `read...FromMetadata` helpers parse stored values. `resolvePlatformSettingsName` supplies the display name. `GetPagePrices` and `GetApprovedRunningSummary` expose price and status summaries; `shouldHideTestAudience` and `filterAudienceSpecLayer` support audience-spec presentation.

`ExportCampaignReport`, `ExportCampaignAudienceClickReport` and `ExportCampaignClickReport` use the durable audience UID/short-code store and filtered click data. Delivery status is `unknown` in the audience report because the durable audience file does not contain delivery status. `campaignReportRow`, `campaignAudienceClickReportRow` and header constants define report shapes; `buildCampaignReportRows`, `buildCampaignAudienceClickReportRows`, `buildCampaignAudienceClickReportRowsFromSortedUniqueUIDs`, `uniqueSortedUIDs`, `actionReportValue` and `activeBundleActionUIDSet` build rows and live action membership. `buildCampaignReportExcel`, `buildCampaignAudienceClickReportExcel` and `excelSafeString` produce spreadsheet output and guard externally supplied values against formula execution. For large multi-campaign exports, see the [asynchronous report guide](campaign-audience-report-job-flow.md).

`CountTargetAudienceFromExcelFile`, `countExcelRows`, `isExcelAsset` and `sanitizeStoredMultimediaPath` validate and count the uploaded audience file. A dedicated Excel audience file treats its first row as a header.

## Refund reconciliation

`ReconcileUndeliveredCampaignRefund` processes one durable reconciliation job, not a read request. `reconcileUndeliveredCampaignRefunds` locks the campaign and financial state, checks delivery and accounting prerequisites and records a refund once. `campaignRefundManualReview` marks inconsistent immutable accounting for manual review. `tryAcquireFlowLock` and `releaseFlowLock` provide a best-effort Redis lock; database transaction and row-level checks remain essential when Redis is unavailable.

`parseAggregatedTotalSent`, `hasProcessedUndeliveredRefund`, `resolveCampaignCostPerMessageFromMetadata` and `parseMetadataUint64` interpret recorded results and prices. `computeFreezeRefundSplit` reconstructs the original free-versus-credit contribution so a refund restores the correct sources; if snapshots cannot be parsed, it conservatively returns the amount as free balance. Refund discovery and retry policy live in the [refund reconciliation repository](campaign-refund-reconciliation-repository.md).

`createAuditLog` records campaign actions with request metadata. When tracing a bug, first identify whether the value came from a draft spec, a frozen selection/price snapshot, live delivery data or a derived report; each has a different update and concurrency boundary.
