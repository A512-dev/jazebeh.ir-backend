# Smart targeting test sampling flow

`business_flow/smart_targeting_sampling_flow.go` implements test-preview jobs as methods of `CampaignFlowImpl`. It snapshots inputs, selects actual test candidates per tag, computes the cost and publishes a durable selection for later finalization. It is distinct from exact capacity and execution selection.

## Data and input identity

`smartTargetingTestSample` represents the computed sample; `smartTargetingTestSamplingInput` holds effective calculation inputs and `smartTargetingTestSamplingIntent` ties the calculation to campaign intent. The calculation version is 2. `smartTargetingTestSamplingHash` identifies the campaign, ordered selected tags, classes and colors. Order matters for allocating overlapping audiences across tags. `checkedSmartTargetingTestAudienceCount` and `checkedCampaignCost` reject arithmetic overflow.

`currentSmartTargetingTestSamplingInput` and `currentSmartTargetingTestSamplingIntent` build the effective snapshot from the campaign and dependencies. `frozenCandooSmartTargetingTestSamplingIntent` handles a narrowly grandfathered complete selection frozen before the Candoo color-policy change, only for already finalized approval/sending campaigns. `currentOrFrozenSmartTargetingTestSamplingIntent` accepts current policy or that specific legacy case; drafts are not grandfathered. `smartTargetingTestSamplingAudienceQuery` builds the repository query.

## Start, poll and reuse

`StartSmartTargetingTestSampling` verifies an owned smart-targeting test campaign and validates effective inputs and pricing before queueing. It snapshots the inputs under the appropriate lock. An unchanged in-flight request can reuse active work, and an unchanged completed current result can be reused; retrying a request should not erase useful progress. `reusableActiveSmartTargetingTestSampling` and `currentSmartTargetingTestSamplingCalculationInput` help decide this.

`GetCurrentSmartTargetingTestSampling` locates the generation for current inputs; `GetSmartTargetingTestSamplingByID` checks ownership for a requested job. `smartTargetingTestSamplingStatusDTO` and `smartTargetingTestSamplingCalculationDTO` expose status and currentness. `isCurrentSmartTargetingTestSampling` checks whether completed work still matches inputs and bundle allocation state; `requireCurrentSmartTargetingTestSampling` enforces that requirement for consumers. A calculated result can later be stale.

## Worker and publication

`ExecuteSmartTargetingTestSamplingCalculation` reconstructs saved input with `samplingInputFromCalculation`, performs the expensive sample scan and publishes the job result and campaign sampling intent atomically. During publication it locks the relevant campaign and holds a bundle share lock so its fingerprint remains consistent with approval/materialization. It recalculates price from the locked campaign state before committing. Repository lease checks prevent an older worker from publishing over a reclaimed calculation.

`calculateSmartTargetingTestSampleForInput` uses shared union-wide score bounds and selects per tag while excluding previously chosen IDs. The sample's satisfied-tag count, effective audience and price drive the test campaign cost. The underlying per-tag query does not promise random or reproducible ordering; see [smart targeting audience repository](smart-targeting-audience-repository.md). `clearCampaignSmartTargetingTestSamplingPreviewFields` clears in-memory preview fields, and `clearCampaignSmartTargetingTestSamplingPreview` persists invalidation after configuration changes. `ownedSmartTargetingTestCampaign` centralizes ownership and phase checks.

The persisted selection is an immutable preview; a separate [test sample reservation](campaign-targeting-test-sample-selection-repository.md) rechecks eligibility during finalization. A successful preview does not guarantee those recipients remain available indefinitely.

## Why order and freshness matter

For example, if tags A and B both contain a profile and A is sampled first, that profile is excluded from B's selection in the same preview. Reordering the tags can therefore change the attributed sample even if the set of selected tags is unchanged. The ordered IDs belong in the input hash and selection snapshot. The effective count is derived from the sampling result and the sample size; checked arithmetic prevents wrapping when computing count or cost.

The preview, its active reservation, and the final bundle allocation are three different records. The preview preserves what the worker selected; finalization reserves those exact members after rechecking availability; later materialization consumes that reservation into a permanent bundle selection. If a profile becomes unavailable between preview and reservation, the solution is a fresh calculation rather than silently substituting a different audience.
